### 6. CI/CD: Автосборка и автообновление десктоп-приложения — 1 марта 2026

#### Проблема
GitHub Actions workflows лежали в `desktop/.github/workflows/` — GitHub их не видит (ищет только `.github/workflows/` в корне репо). Релизы никогда не собирались автоматически.

#### Что сделано
- **Перенесены workflows в корень репо:**
  - `desktop/.github/workflows/build.yml` → `.github/workflows/desktop-build.yml`
  - `desktop/.github/workflows/release-please.yml` → `.github/workflows/desktop-release.yml`
- **Добавлен `defaults.run.working-directory: desktop`** ко всем jobs
- **Добавлен `paths: ["desktop/**"]`** — workflows триггерятся только при изменениях в desktop/
- **Упрощён release workflow (только Windows):**
  - Убрана матрица `[ubuntu-latest, windows-latest, macos-latest]` → только `windows-latest`
  - Убраны шаги macOS x64 и Linux arm64
  - Заменён GitHub App token на `GITHUB_TOKEN`
- **Обновлены пути release-please:** `config-file: desktop/release-please-config.json`, `manifest-file: desktop/.release-please-manifest.json`, пакет `"desktop"` вместо `"."`
- **Удалены старые файлы** `desktop/.github/workflows/build.yml` и `release-please.yml`

#### Как это работает
1. Push в main с изменениями в `desktop/` → GitHub Actions запускает `desktop-release.yml`
2. Release Please создаёт Release PR с бампом версии
3. Merge Release PR → `publish-release` job собирает `.exe` на `windows-latest` и загружает в GitHub Releases
4. `update-electron-app` (уже настроен в десктопе) проверяет GitHub Releases → автообновление

### 🔴 Этап 7: Защита данных и архивирование сообщений

> **Цель:** Шифрование сообщений в БД, сжатие для экономии места, архив удалённых сообщений с хранением 3 года.

#### 7.1 Архив удалённых сообщений

**Проблема:** Сейчас при удалении сообщение уничтожается из MongoDB навсегда (hard delete). Нет возможности восстановить или проверить удалённое.

**Решение:**
1. Создать коллекцию `messages_archive` в MongoDB
2. При удалении сообщения — перемещать документ в `messages_archive` вместо удаления
3. Добавить поле `deleted_at: DateTime` и `deleted_by: UserId`
4. Настроить TTL-индекс на `deleted_at` с expireAfterSeconds = 94608000 (3 года)
5. MongoDB автоматически удалит записи старше 3 лет

**Затронутые файлы (Rust backend):**
- `server/crates/core/database/src/models/messages/model.rs` — метод `delete()`: вместо `delete_message()` → `archive_message()` + `delete_message()`
- `server/crates/core/database/src/drivers/mongodb/messages.rs` — новый метод `archive_message()`
- Bulk delete тоже нужно обновить

**API для администраторов:**
- `GET /admin/archive?channel=X&before=DATE` — просмотр архива
- `POST /admin/archive/:id/restore` — восстановление сообщения

#### 7.2 Шифрование сообщений в БД (Encryption at Rest)

**Проблема:** Сообщения хранятся в MongoDB plain text. Файлы уже шифруются AES-256-GCM, а сообщения — нет.

**Решение:**
1. Использовать существующий `encryption_key` из `[files]` или добавить отдельный `[messages] encryption_key`
2. AES-256-GCM шифрование поля `content` перед записью в MongoDB
3. Расшифровка при чтении из БД (прозрачно для API)
4. Хранить nonce (IV) вместе с зашифрованным текстом (prefix 12 bytes)
5. Индексирование: для поиска по сообщениям — хранить отдельный HMAC-хеш или использовать MongoDB Client-Side Field Level Encryption (CSFLE)

**Затронутые файлы (Rust backend):**
- `server/crates/core/database/src/models/messages/` — encrypt на write, decrypt на read
- `server/crates/core/config/src/lib.rs` — новая секция `[messages]` с ключом
- `Revolt.toml.template` — добавить `[messages] encryption_key`
- Поиск сообщений (`search`) — адаптировать под шифрование

**Ограничения:**
- Поиск по зашифрованным сообщениям невозможен без дополнительного индекса
- Варианты: MongoDB CSFLE (Enterprise), blind index (HMAC), или поисковый индекс отдельно

#### 7.3 Сжатие сообщений

**Проблема:** Сообщения хранятся без сжатия. При росте базы — лишний расход диска и памяти.

**Решение:**
1. Сжатие `content` через zstd (или lz4) перед шифрованием
2. Порядок: content → compress → encrypt → store
3. Чтение: store → decrypt → decompress → content
4. Флаг `compressed: bool` в документе для обратной совместимости

**Оценка выигрыша:**
- Текстовые сообщения сжимаются в 2-4 раза (zstd level 3)
- Короткие сообщения (< 50 байт) — не сжимать (overhead больше выигрыша)
- Порог сжатия: только сообщения > 100 байт

| # | Задача | Сложность | Статус |
|---|--------|-----------|--------|
| 1 | Модуль сжатия (zstd/lz4) с порогом | Низкая | ⬜ |
| 2 | Интеграция в pipeline: compress → encrypt → store | Средняя | ⬜ |
| 3 | Обратная совместимость (флаг `compressed`) | Низкая | ⬜ |

#### Порядок реализации Этапа 7

```
Шаг 1: Архив удалённых (7.1) — самое простое, сразу даёт ценность
Шаг 2: Шифрование (7.2) — после архива, т.к. архив тоже должен шифроваться
Шаг 3: Сжатие (7.3) — последнее, pipeline: compress → encrypt → store
```
